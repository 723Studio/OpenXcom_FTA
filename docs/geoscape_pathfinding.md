# Геоскейп: ограничение маршрутов Craft по суше/воде (проектирование)

## Контекст
Сейчас в GeoscapeState игрок может отправить Craft в любую точку на Globe, и Craft летит по кратчайшей прямолинейной дуге (в радиальных координатах на сфере). Globe визуально построен из набора polygon (RuleGlobe), где polygon с texture условно представляет «сушу», а области без polygon — «море/океан».

Требование: добавить новый режим маршрутизации Craft на глобусе, зависящий от нового свойства RuleCraft `pathfinding`:

- `BOTH` (по умолчанию): поведение без изменений — прямолинейное движение по кратчайшему пути.
- `ONLY_LAND`: конечная точка и весь маршрут (включая промежуточные точки) должны проходить только по «суше».
- `ONLY_WATER`: конечная точка и весь маршрут должны проходить только по «воде», то есть не заходить на полигоны суши.

Важно: по этой задаче **пока не реализуем код**, только проектируем и уточняем требования.

---

## Термины и определения (предлагаемые)
Нужны чёткие определения, иначе в углах будут разные трактовки:

- **Land / суша**: точка (lon/lat) считается сушей, если попадает внутрь polygon, у которого texture **НЕ** помечена как `isOcean: true` и **НЕ** помечена как `fakeUnderwater: true`.
- **Water / вода**: точка (lon/lat) считается водой, если:
   - НЕ попадает внутрь суши (комплемент области суши — «область без polygon суши»), **или**
   - попадает в polygon с texture, у которой `isOcean: true`, **или**
   - попадает в polygon с texture, у которой `fakeUnderwater: true`.

Договорённость: `fakeUnderwater` трактуем как «вода»; также любые `isOcean`-текстуры трактуем как «вода». Все прочие текстуры — «суша».

---

## Где брать информацию о суше/воде
Уже есть (или предполагается, что есть) проверки вида:

- `Globe::insideLand(lon, lat)` — похоже на готовую функцию “точка в суше”.
- `Globe::getPolygonFromLonLat(lon, lat)` — возвращает polygon под точкой.
- `RuleGlobe::getTexture(id)` и `Texture::{isOcean, fakeUnderwater}` — возможные признаки классификации.

Ключевой момент: нам нужна **быстрая** функция `IsAllowed(lon, lat, mode)` для A*/поиска пути.

## Идея архитектуры (минимально-инвазивная)
### Основная мысль
Не ломать текущую механику движения (которая умеет двигаться “по прямой”), а добавить **маршрут как набор промежуточных точек** (waypoints) на сфере.

Примечание: сейчас в игре нет промежуточных waypoints как сущности управления маршрутом — есть текущая позиция и конечная цель. Здесь под waypoints подразумеваются **внутренние** (технические) точки маршрута, которые движок будет использовать для последовательного движения сегментами.

- В режиме `BOTH`: 0 промежуточных точек, как сейчас.
- В `ONLY_LAND`/`ONLY_WATER`: вычисляем путь как последовательность узлов на поверхности (lon/lat), и дальше Craft движется по отрезкам/дугам между этими узлами, используя существующий прямолинейный шаговый механизм на каждом сегменте.

То есть: мы добавляем путь, но переиспользуем старую “физику перемещения” между соседними точками.

### Где считать путь
На этапе назначения пункта назначения (клик по глобусу / выбор цели):
- Если `BOTH` — как сейчас.
- Если ограниченный режим — пытаемся построить маршрут.

## Варианты алгоритма (с плюсами/минусами)
Ниже 3 реалистичных подхода. Для начала стоит выбрать один как базовый.

Выбор для реализации:
- **Вариант C** — основной (делаем сейчас).
- **Вариант B** — запасной (если C не устроит по качеству маршрутов/производительности).
- **Вариант A** — отвергнут, так как важная концепция игры: на глобусе нет сетки и всё работает в реальных координатах.

### Вариант A (рекомендуемый для MVP): дискретная сетка на сфере + A*
1) Создаём фиксированную сетку по долготе/широте (например, шаг 1°/2°/5° — настраиваемо).
2) Каждая ячейка/узел — это точка (lon, lat) в центре клетки.
3) Помечаем узлы как `land`/`water` через `insideLand()` (или эквивалент).
4) Делаем граф соседей (4/8 направлений; лучше 8).
5) Запускаем A* от старта к цели по допустимым узлам.
6) Полученный путь **сглаживаем**: пробуем заменить «ломаную» последовательность узлов более длинными сегментами ("пробросить дугу") между далёкими узлами, каждый раз проверяя дискретной выборкой, что дуга не пересекает запрет.

Плюсы:
- Простая реализация и отладка.
- Можно гарантировать: все точки пути допустимы (узлы).
- Гибко балансируется точность/скорость через шаг сетки.

Минусы:
- Базовый путь на сетке ступенчатый; поэтому **сглаживание обязательно**, иначе маршрут будет выглядеть “ломаным”.
- Проверка “дуга между узлами целиком по суше/воде” требует дополнительной дискретной проверки по дуге.

### Вариант B: граф смежности polygon (навигация по «нави‑мешу»)
1) Строим граф polygon суши (или наоборот — водных областей, если они представлены отдельными полигонами).
2) Смежность определяем по общим рёбрам/вершинам (или по близости, что сложнее).
3) Ищем путь по polygon.
4) Путь превращаем в последовательность контрольных точек (например, через центроиды polygon/переходы через рёбра).

Плюсы:
- В теории ближе к геометрии карты.

Минусы:
- Данные polygon в WORLD.DAT/Rules часто не дают идеальной топологии (стыки, щели, перекрытия).
- Сложно и рискованно по времени разработки.
- Для `ONLY_WATER` без явных “водных polygon” практически не применимо.

### Вариант C: растеризация “маски” суша/вода в карту + поиск пути по пикселям
1) Растеризуем сушу в 2D карту (equirectangular) с фиксированным разрешением (например, 720x360).
2) Получаем бинарную маску суши.
3) По маске ищем путь (A*) в 2D.
4) Конвертим пиксельные координаты обратно в lon/lat.

Важно: несмотря на внутреннюю дискретизацию, наружу путь должен быть представлен как **плавная линия** в lon/lat (см. требование к сглаживанию и проверке дуг сэмплированием).

#### Конкретика для варианта C (параметры и сглаживание)
Цель: внутренняя дискретизация не должна «торчать» в маршруте, а ограничения land/water должны соблюдаться на всей дуге с целевой точностью около $0.002$ рад.

**1) Двухуровневая маска (рекомендуется)**
- `maskFine` — высокая точность для проверок `IsAllowed()` и валидации дуг.
   - Рекомендуемый размер: `Wf=4096`, `Hf=2048`.
   - Тогда размер ячейки по долготе: $\Delta\lambda=\frac{2\pi}{W_f}\approx 0.00153$ рад.
   - По широте: $\Delta\varphi=\frac{\pi}{H_f}\approx 0.00153$ рад.
   - Это сопоставимо с ~10 км и хорошо согласуется с шагом $0.002$ рад.
- `gridCoarse` — более грубый грид для поиска пути (A*), чтобы не гонять A* по миллионам узлов.
   - Рекомендуемый размер: `Wc=1024`, `Hc=512` (или `2048x1024` если по производительности ок).
   - Узел coarse считается проходимым, если в соответствующем блоке `maskFine` большинство (или все) семплы соответствуют нужной категории.

Идея: A* работает по `gridCoarse`, а когда получаем путь — сглаживаем и валидируем каждый длинный сегмент по `maskFine` с шагом $0.002$ рад.

**2) Маппинг lon/lat → индексы маски**
- Долгота: $\lambda\in[-\pi,\pi)$.
   - `x = floor((lambda + pi) / (2*pi) * W)` с wrap по модулю `W`.
- Широта: $\varphi\in[-\pi/2,\pi/2]`.
   - `y = floor((phi + pi/2) / pi * H)` с clamp в `[0, H-1]`.

**3) Полярные шапки**
- Если $|\varphi| > \frac{\pi}{2} - 0.01$, в `maskFine` можно принудительно маркировать как сушу.
- Для `ONLY_WATER` эти области будут блокироваться как суша.

**4) Построение и сглаживание маршрута (чтобы линия была плавной)**
1) Построить «сырой» путь на `gridCoarse` как список узлов (x,y).
2) Преобразовать узлы в lon/lat (центры ячеек) → получится ломаная.
3) Сгладить ломаную **упрощением по видимости** (greedy shortcutting):
    - Идём по списку точек: пытаемся заменить цепочку `Pi..Pj` одним сегментом `Pi→Pj` (дуга по большой окружности).
    - Сегмент допустим, если при дискретной проверке по дуге (шагом $\le 0.002$ рад по центральному углу) все сэмплы проходят `IsAllowed()` по `maskFine`.
    - Берём максимально дальний `j`, который проходит проверку; добавляем его и продолжаем.

Результат: маршрут хранится как небольшое число **длинных геодезических сегментов** (а не как частая “лесенка”), и визуально выглядит как плавная линия.

**5) Проверка длины пути для топлива**
- Длину пути считаем как сумму длины дуг между контрольными точками (по центральному углу на сфере). Для сегмента: $d = R\cdot\Delta\sigma$, где $\Delta\sigma$ — центральный угол.
- $R$ должен совпадать с тем, что используется в текущей логике дальности/топлива (или нужно явно выбрать константу, совместимую с существующим кодом).

Плюсы:
- Быстро проверять ограничения (маска — O(1)).
- Для `ONLY_WATER` естественно (комплемент).

Минусы:
- Надо аккуратно работать с wrap по долготе и искажениями на полюсах.
- Придётся отдельно решать “геодезическую стоимость” (чтобы не было сильных артефактов).

## Проверка корректности “маршрут целиком по суше/воде”
Даже если промежуточные точки допустимы, сегмент между ними может пересечь запрет (например, перепрыгнуть пролив).

Зафиксированное требование: **вся дуга движения Craft должна проходить по допустимой области** (суша для `ONLY_LAND`, вода для `ONLY_WATER`), а не только отдельные точки.

Для гарантий предлагается правило:
- Для каждого сегмента пути (между двумя соседними точками маршрута) делать дискретную проверку вдоль большой окружности: взять сэмплы по дуге и требовать, чтобы все сэмплы были допустимы.
- Шаг сэмплирования задаётся целевой точностью (см. ниже) и подбирается при разработке.

Это нужно, чтобы условие “все промежуточные точки” реально выполнялось не только на узлах.

---

## Поведение при недостижимости цели
Нужно определить UX/правила игры, если для `ONLY_LAND`/`ONLY_WATER` цель недостижима:
- Вариант 1: запретить выбор точки/цели сразу (показать сообщение), если точка не в допустимой области.
- Вариант 2: разрешить выбор, но маршрут не строится → сообщение “Невозможно проложить маршрут”.
- Вариант 3: автокоррекция — сдвинуть конечную точку к ближайшей допустимой точке (обычно спорно).

Для начала логичнее: **не строится маршрут → понятное сообщение**, без автосдвига.

Зафиксировано (UX): при недоступной точке назначения показывать **новый State** с текстом о том, что точка назначения недоступна — по аналогии с текущим поведением, когда игрок пытается построить базу не на суше.

Зафиксировано (топливо/дальность): у Craft есть ограничение по дальности (запас топлива). Если по рассчитанному пути Craft не сможет достигнуть точки назначения из-за нехватки топлива, показывать **новый State** с сообщением о невозможности достигнуть выбранной точки назначения.

## Уточняющие вопросы (перед реализацией)
Пожалуйста, ответьте на вопросы — от них зависит и выбор алгоритма, и детали поведения.

### 1) Что именно считается “сушей” и “водой” в данных?
1.1. Зафиксировано: все текстуры, кроме `fakeUnderwater`/`isOcean`, считаются сушей; `fakeUnderwater` и `isOcean` считаются водой.
1.2. Зафиксировано: если polygon ссылается на texture id, которого нет в `RuleGlobe::textures` (в правилах), трактуем это как **сушу** (дефолт для совместимости).
1.3. Зафиксировано: `fakeUnderwater` — это всегда вода, даже если геометрически лежит «внутри суши».

### 2) Что такое “промежуточные точки должны быть в рамках суши”?
2.1. Зафиксировано: **вся дуга движения** должна быть на суше/воде.
2.2. Начальная целевая точность (для проверки дуг/границ): около 10 км, то есть примерно $0.001567$ рад; можно округлить до $0.002$ рад. Точность допускается подобрать/уточнить при разработке.

### 3) Какой ожидаемый UX при клике на запретную точку?
3.1. Зафиксировано: показывать новый State с текстом “точка назначения недоступна” (аналогично попытке построить базу не на суше). Автосдвиг к ближайшей допустимой точке не делать.
3.2. Дополнение: если точка допустима по типу поверхности, но **недостижима по дальности топлива** с учётом построенного пути, показывать новый State с сообщением о невозможности достигнуть точки.

### 4) Нужна ли маршрутизация для всех типов “целей” одинаково?
4.1. Зафиксировано: для перехвата UFO маршрут тоже должен уважать ограничение (`ONLY_LAND`/`ONLY_WATER`). Так как UFO двигается, путь нужно **пересчитывать при каждом изменении положения UFO**. Если UFO переходит в состояние `landed`, её координаты не меняются и пересчёт по позиции не требуется.
4.2. Зафиксировано: для “патруля/автопатруля” и waypoint применяются те же правила.

### 5) Производительность и кэширование
5.1. Оценка: одновременно активных Craft обычно не более 10.
5.2. Зафиксировано: если цель — UFO, пересчёт пути выполняется **при каждом изменении координат UFO** (кроме состояния `landed`, где координаты не меняются).
5.3. Зафиксировано: маску land/water (по выбранной дискретизации) можно кэшировать один раз, так как ruleset не меняется в процессе игры и полигоны статичны. Допускается даже предрасчёт до запуска игры.

Примечание про будущее: если будет добавлена механика терраформирования (смена texture из-за активности пришельцев), она не должна переводить текстуры между категориями «суша»/«вода». Значит базовая классификация land/water остаётся неизменной и кэш валиден.

### 6) Спорные географические места
6.1. Зафиксировано: если узкий пролив/канал “исчезает” из-за дискретизации, это допустимо, пока ошибка не выходит за пределы целевой погрешности (порядка $0.002$ рад / ~10 км). При этом итоговый путь всё равно должен визуально быть плавным (см. требование к сглаживанию), а корректность дуг проверяется сэмплированием.
6.2. Зафиксировано: допускается особая обработка полюсов для упрощения. Так как полярные области заняты льдами, которые считаются сушей, можно ввести «полярные шапки» радиусом примерно $0.01$ рад вокруг каждого полюса и считать их **всегда сушей**.

При этом базовые требования сохраняются:
- для `ONLY_LAND` такие зоны допустимы как суша;
- для `ONLY_WATER` такие зоны недопустимы как суша.

Также по-прежнему нужно корректно обрабатывать wrap по долготе (±π) и крайние широты (около ±π/2), без артефактов и падений.

## Риски
- Геометрия polygon может иметь щели/перекрытия → классификация точки может быть шумной на береговой линии.
- Слишком крупный шаг сетки делает маршруты “неправдоподобными”; слишком мелкий — дорого по CPU.
- Для `ONLY_WATER` при определении воды как “всё кроме суши” могут возникнуть пути, которые проходят по “пограничным” пикселям из-за дискретизации.
